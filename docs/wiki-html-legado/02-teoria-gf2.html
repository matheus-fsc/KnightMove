2. GF(2) e Espaço de Ciclos

De onde sai o espaço $\mathbb{F}_2$ neste projeto: a história começa com loops — caminhos que saem de uma casa e voltam a ela — e termina com tours sendo vetores binários.

1. A motivação: o que é um loop?

No grafo do cavalo, um loop é um caminho fechado: sai de uma casa, segue uma sequência de movimentos de cavalo, e retorna à casa inicial sem repetir nenhuma aresta. Visualmente, é um círculo no grafo.

Antes de qualquer formalismo, vale ver os loops em ação. O modo “Loops” do visualizador anima cada ciclo fundamental do tabuleiro 8×8 — são 105 no total:

Visualizador (selecione o modo Loops no menu superior) abrir em janela cheia ↗

Cada loop aparece em dois pedaços: um caminho laranja e um caminho azul, que se encontram numa aresta amarela — a “colisão” que fecha o ciclo. A próxima seção explica por que essa estrutura em dois caminhos é exatamente a forma natural de descrever uma base de loops.

2. Como o algoritmo encontra os loops

A pergunta é prática: o tabuleiro $n \times n$ tem $\beta_1(n) = |E| - |V| + 1$ loops independentes (ver a tabela na Seção 6). Como o código descobre exatamente esses loops?

A técnica é clássica e usa uma árvore geradora por BFS a partir de uma casa raiz (no projeto, a casa (0,0)). O fato central é:

Cada aresta fora da árvore geradora fecha exatamente um ciclo fundamental — e essas são todas as $\beta_1$ dimensões do espaço de ciclos.

2.1 O procedimento, passo a passo

def compute_bfs(adj, start=(0, 0)):
    """BFS a partir de start; devolve a árvore geradora."""
    parent      = {start: None}
    level       = {start: 0}
    order       = [start]
    queue       = deque([start])
    tree_edges  = set()
    while queue:
        u = queue.popleft()
        for v in adj[u]:
            if v not in parent:           # aresta de árvore
                parent[v] = u
                level[v]  = level[u] + 1
                order.append(v)
                queue.append(v)
                tree_edges.add(tuple(sorted([u, v])))
    return parent, level, order, tree_edges

A BFS visita todos os $V$ vértices e seleciona exatamente $V-1$ arestas para a árvore. Sobram $|E| - (V-1) = \beta_1$ arestas “extras”. Cada uma delas, quando combinada com o caminho de árvore entre seus dois endpoints, forma um ciclo. Esse conjunto de $\beta_1$ ciclos é uma base do espaço de ciclos — qualquer outro loop é uma combinação (em GF(2)) deles.

3. Como cada loop é armazenado

Uma vez encontrada uma aresta não-árvore $e = \{u, v\}$, o ciclo é gerado por três peças:

  1. caminho1: trajeto na árvore da raiz até $u$;
  2. caminho2: trajeto na árvore da raiz até $v$;
  3. colisao: a própria aresta $e = \{u, v\}$.

Implementação literal no projeto:

def loops_from_bfs(parent, tree_edges, edges):
    loops = []
    for e in sorted(edges):
        if e in tree_edges:
            continue
        u, v = e
        loops.append({
            "caminho1":      reconstruct_path(u, parent),
            "caminho2":      reconstruct_path(v, parent),
            "colisao":       [u, v],
            "tamanho_ciclo": len(...) + len(...),
        })
    return loops

3.1 Por que dois caminhos e não um ciclo direto?

Os dois caminhos compartilham um prefixo: tudo desde a raiz até o menor ancestral comum (LCA) de $u$ e $v$. Esse prefixo aparece duas vezes — uma em caminho1, outra em caminho2. Se simplesmente concatenássemos as arestas, cada aresta do prefixo seria contada duas vezes.

A solução é elegante: combinar as arestas com a operação XOR. Uma aresta presente duas vezes ($1 \oplus 1 = 0$) se cancela, e sobram apenas as arestas que pertencem genuinamente ao ciclo. Função correspondente no front-end: 

// js/core.js — extrai as arestas do ciclo via XOR
export function getLoopEdges(loop) {
  const edges = new Set();
  const toggle = (u, v) => {
    const k = edgeKey(u, v);
    if (edges.has(k)) edges.delete(k);   // 1 ⊕ 1 = 0
    else              edges.add(k);      // 0 ⊕ 1 = 1
  };
  const c1 = loop.caminho1, c2 = loop.caminho2;
  for (let i = 0; i < c1.length - 1; i++) toggle(c1[i], c1[i + 1]);
  for (let i = 0; i < c2.length - 1; i++) toggle(c2[i], c2[i + 1]);
  toggle(loop.colisao[0], loop.colisao[1]);
  return edges;
}

A função toggle é literalmente uma operação XOR sobre o conjunto de arestas. O prefixo comum cancela automaticamente — é o primeiro lugar onde GF(2) aparece de forma operacional no projeto.

4. De loops a vetores: GF(2) entra em cena

Numere as arestas de $1$ a $|E|$. A cada loop $\ell$ associe um vetor $\mathbf{1}_\ell \in \{0,1\}^{|E|}$:

\[ \mathbf{1}_\ell[e] \;=\; \begin{cases} 1 & \text{se a aresta $e$ pertence ao loop} \\ 0 & \text{caso contrário} \end{cases} \]

A operação natural — “loop A combinado com loop B, cancelando as arestas comuns” — é exatamente a soma coordenada-a-coordenada com $1+1=0$:

\[ (\mathbf{1}_A \oplus \mathbf{1}_B)[e] \;=\; \mathbf{1}_A[e] + \mathbf{1}_B[e] \pmod{2} \]

4.1 O corpo $\mathbb{F}_2$

$\mathbb{F}_2$ (também escrito $\text{GF}(2)$) é o corpo com dois elementos $\{0, 1\}$ e a aritmética:

+01
001
110

É a aritmética do XOR dos programadores. Tudo o que segue é álgebra linear comum, mas com escalares neste corpo.

5. Tours também são vetores

Exatamente a mesma codificação serve para um tour fechado $t$: $\mathbf{1}_t[e] = 1$ se a aresta $e$ é usada por $t$, $0$ caso contrário. Como um tour visita cada vértice exatamente uma vez com dois movimentos (entra e sai), em cada vértice $v$ usa exatamente 2 arestas incidentes.

Essa restrição se escreve em GF(2) usando a matriz de incidência $\partial_1 \in \mathbb{F}_2^{V \times E}$ (linha $v$, coluna $e$, vale $1$ se $v \in e$):

\[ \partial_1 \cdot \mathbf{1}_t \;=\; \mathbf{0} \pmod{2} \]

Isso diz que cada vértice tem grau par em $\mathbf{1}_t$. Como o tour não passa duas vezes por nenhum vértice e cada vértice é visitado, o grau é exatamente $2$. Logo todo tour é um elemento do espaço de ciclos:

\[ Z_1(G; \mathbb{F}_2) \;:=\; \ker(\partial_1) \;\subseteq\; \mathbb{F}_2^{|E|} \]

6. O número de Betti $\beta_1$

A dimensão de $Z_1(G; \mathbb{F}_2)$ é o primeiro número de Betti do grafo:

\[ \beta_1(n) \;=\; |E_n| - |V_n| + 1 \]

É exatamente a contagem de “arestas fora da árvore BFS” que a Seção 2 deu. Para o grafo do cavalo $n \times n$:

Para o tabuleiro 8×8 mostrado no visualizador, $\beta_1 = 168 - 64 + 1 = 105$ — exatamente o número de loops animados acima.

7. Onde os tours vivem dentro de $Z_1$

Seja $\text{Ham}(n) \subseteq Z_1(G_n; \mathbb{F}_2)$ o subespaço gerado pelos vetores indicadores de todos os tours hamiltonianos fechados. Como todo tour satisfaz $\partial_1 \cdot \mathbf{1}_t = 0$, temos a inclusão:

$\mathbb{F}_2^{|E|}$ ⊃ $Z_1$ = ker($\partial_1$) ⊃ Span(Ham) ↑ ↑ $\beta_1$ dimensões $\beta_1 - ?$ dimensões

A pergunta natural é: quantas dimensões $\beta_1 - \text{rank}(\text{Ham})$ “faltam”? Esse número se chama deficit:

\[ \text{deficit}(n) \;:=\; \beta_1(n) - \text{rank}_{\mathbb{F}_2}(\text{Ham}(n)) \]
